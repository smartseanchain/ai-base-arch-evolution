分析引擎 · 方法与演进总线

整站鸟瞰见 总览 · 三问导读。本页是分析读数仪表盘：analysis_engine 在 evolution-manifest.json 与 evolution-candidates.json 上产出模块/因子热力、共现、规则提示、相较上期 diff、闭环缺口与运行血缘（run_id / repo_revision）。可与 推演·方法（持续迭代、跨学科办法）、进化闭环、战略·舆情 · 多源台 对表；全文仍为非预测的定性脚手架。

本页侧重：只读分析快照与热力；首次读建议 → 读站指路；改规则 / 管道 / 合 PR → docs · 最短链（0c） · 真源分层 · 前后台 · 组件×主链 · 维护导读 · 不变量索引 · PR 证据三联；枢纽 关系视图 / 系统边界 见下条「架构与读数总线」。

脚本入口：仓库内 scripts/analysis_engine.py；正文内节号与插槽对照见 推演·方法。

方法与认识论：RESEARCH_METHODS_MAP（方法索引与 A/B/C 可利用性）、DEDUCTION_STRATEGY（单轮七步）。

架构与读数总线：ONE_PAGER · 架构师五步 · 不变量索引 · PR 证据三联；PLATFORM_MASTER_MAP · 读者面/管理面；ARCHITECTURE · 七类模块；SITE_DATA_UPDATE_FRAMEWORK（site-data-bus.js）；DATA_ANALYSIS_SITE_CONTENT_SYNC；维护导读 · 关系视图 · 系统边界 · 衔接矩阵。

数据与运行：提示落实/否决记在 assets/evolution-hint-decisions.json（双周运行手册）。沉淀与趋势：data/sediment.json 按日摘要，双写 data/evolution.db；sediment_trends.py → assets/sediment-trends.json。规则之上的模型/RAG 见 智能进化（方法篇插槽⑨）。

1.3 研究方法（§12）→ 用引擎哪类读数

详表见 RESEARCH_METHODS_MAP；此处列与仪表盘最直接相关的用法。

方法族（§12）优先看引擎里什么常与谁并读
情景规划 / 三簇跨日后 sediment-trends 覆盖率 + 当日热力 Top 是否稳定重叠§8、沙盘
系统动力学 / 反馈环共现对是否持续上升（cooccurrence）+ diff 提示「共现增强」§3、配方传导链
FTA / FMEA / 敏感性因子热力顺序变化 + 沙盘依赖流（站内核 A 级）§7「谁先绷紧」
因果推断（思想）改 manifest 一条前提后重跑，看 evolution_hints 是否断链式消失§2
红队 / 危机人为加压后 Top 模块是否突变 + hint_closure_gaps 是否增条地缘、§7 增行纪律
质性 / 五维切片把「可见征候」写成可映射 maps_to.pages 的信号再入库 → 热力验证§9

想象：若某方法族在引擎读数上长期得不到任何支持（热力平、无共现、无规则触发），要么该叙事仍停留在话语层，要么 maps_to 映射过粗——应回到 进化闭环 细化编码或回到 §2 判据降级处理。

2. 引擎产出字段与契约（读 JSON 时对齐）

assets/analysis-snapshot.json 由 analysis_engine.py 写入；CI 与 make validate 用 jsonschema 对照 docs/schemas/analysis-snapshot.schema.json。下列为阅读仪表盘与自助脚本时的字段导游。

字段（顶层或关键子结构）含义
schema_version当前为 1；大改时递增并同步校验脚本
generated_atISO8601 时间戳（北京时间 Asia/Shanghai，+08:00）
run.run_id / run.repo_revision单次运行血缘，与当日 sediment / SQLite 对齐
sources含 combined_for_analysis、manifest/候选计数、candidate_review_breakdown、hint_decisions 汇总等
module_heat / factor_heat站内页与沙盘因子出现频次 Top 列表
kind_distribution信号 kind（opinion/policy/law/…）计数分布
cooccurrence同一信号内因子两两共现 Top
evolution_hints规则模板命中 + 可选「相较上期快照」的 diff 提示 + Top 因子模板/兜底句；对象可含 rule_id、target_pages
hint_closure_gapstrack_closure 已触发但决策 JSON 尚无 done/rejected 的 rule_id 列表

模式：python3 scripts/analysis_engine.py --check 与 --dry-run 等价，跑全部分析逻辑并校验结构，不写快照文件（CI 用）。日常写回加 --sediment 以追加沉淀与趋势链。

3. 在「自我进化」闭环中的位置

抓取（ingest）→ 候选 → 审阅合并（manifest）→ 本页分析 → 根据提示回到 综合推演 §11 增删配方/表行 → 沙盘 压测。分析引擎是反馈环的量化侧，不替代定性判断。

  • 输入：与 evolution.js 同源的两份 JSON（已入库 + 待审）。
  • 输出：analysis-snapshot.json（仪表盘数据）+ 可选 data/sediment.json（按日一条摘要）。
  • 扩展插槽 ⑧（§11）：当热力或共现长期偏斜时，触发对 §6/§7 的专项审阅——见 §11 列表。

4. 数据沉淀

data/sediment.json 在运行 analysis_engine.py --sediment 时按日更新一条（同日重复运行会覆盖当日记录），字段含 manifest/候选条数、热力 Top 因子与页面。不包含外链全文，体量可控。

长期沉淀建议：将本文件纳入定期备份（仓库外对象存储、加密盘或按月快照）；历史条目勿随意删，以便 趋势脚本 计算「多日 Top 覆盖率」。若条目极多，可只保留近年 + 冷归档旧文件，分析前合并为一份再跑脚本。

SQLite（data/evolution.db）

启用 --sediment 时与 JSON双写同一日摘要（标准库 sqlite3，无额外依赖）。表 sediment_entry 按日主键，便于 SQL 查询与后续扩展（BI、导出）。sediment_trends.py 在「SQLite 行数 ≥ JSON 条数」时优先读库，否则仍读 JSON，避免单机未建库时失配。

历史 JSON 仅存在仓库、尚未有库时，可一次性导入：

python3 scripts/import_sediment_json_to_sqlite.py

默认 .gitignore 忽略 data/evolution.db，以 JSON 为可提交主副本；若团队希望共享库文件，可删除该忽略项并约定备份策略。

5. 长期趋势（跨日汇总）

单日 snapshot 看当下结构；跨日看谁一直在 Top。运行 python3 scripts/sediment_trends.py，优先从 SQLite 读多日行（否则读 data/sediment.json），生成 assets/sediment-trends.json（因子/页面「出现在 Top 的天数」与覆盖率、简要提示）。分析仪表盘会在快照下方自动追加「长期沉淀与趋势」卡片（需 HTTP 打开页面）。无多日数据时脚本仍写出占位 JSON，提示先积累沉淀。

6. 分析仪表盘（实时自 snapshot）

需本地 HTTP 打开页面以加载 JSON。若空白，请先运行下方命令生成快照。仪表盘顶部有聚合解读卡片：由 analysis.js 将当日快照与（若已加载）sediment-trends.json 拼成可读摘要，可一键复制 Markdown。若存在 assets/ai-analysis-overlay.json（可选；见 AI 解读层），仪表盘底部会追加独立区块展示，并与当前快照 run_id 对读。

7. 命令

分析引擎 · CLI 
python3 scripts/analysis_engine.py
python3 scripts/analysis_engine.py --check
python3 scripts/analysis_engine.py --dry-run
python3 scripts/analysis_engine.py --sediment
python3 scripts/sediment_trends.py

建议流水线：ingest →（审阅）merge → analysis_engine（加 --sediment）→ sediment_trends.py → 打开本页与 进化闭环 对照。双周节奏：运行手册。对账：check_manifest_drift.py + scripts/evolution-registry.json（页面白名单、因子与 lab.js 一致、ingest 配置与 sitemap PRIORITY）。长期工程视图见 整体改造。

8. 持续更新

把「分析 + 沉淀 + 趋势」固化为可重复的一键步骤，便于本机 cron 或 CI 挂钟。

一键（推荐）：

bash scripts/run_update_pipeline.sh
# 或
make analyze

已校验后快速重算（双周内多轮）：make evolution-fast 或 bash scripts/run_analyze_write.sh——仅写快照/沉淀/趋势 + 快照契约 + --check，跳过 manifest/漂移/单测/顶栏；提交前仍须 make validate。见 EVOLUTION_RUNBOOK · 加速。

完整 make analyze 等价于顺序执行：compileall → 校验 manifest / 候选 / hint 决策 → registry JSON Schema → 对账 → navLinks → 顶栏 → 单测 → analysis_engine.py --sediment → sediment_trends.py → 沉淀·趋势 Schema → 快照 Schema → --check（与 run_validate.sh 闸门对齐至单测为止）。命令表见 scripts/README.md。完成后将变更提交到 Git（若希望站点随仓库刷新），或只做本地预览。

可读摘要（无 LLM）：仓库根执行 make digest 输出 Markdown 截面（热力、共现、闭环缺口、趋势表等），便于贴 PR 或复盘；与 diff_analysis_snapshot.py --git … 两版 diff 互补。说明见 智能进化 · 进化摘要。

本机定时：在 macOS/Linux 用 cron 或 launchd 每日/每周调用上述脚本；注意工作目录为仓库根。

GitHub Actions：update-pipeline.yml——分析侧，手动 + 每周定时，artifact 下载 JSON，默认不回写仓库（站点与 Git 对齐仍靠本地 make analyze 后提交）。ingest-pipeline.yml——抓取候选，手动 + 每周定时，artifact 含 evolution-candidates.json 与运行摘要。ci.yml：校验 + 对账 + scripts/tests 单测 + analysis_engine.py --check。本地可选 bash scripts/install-git-hooks.sh 启用近同 pre-commit。细节见仓库根 README「持续集成」。

抓取 ingest仍建议单独排期（见 进化闭环 · 抓取），审阅后再 merge；勿与纯分析流水线绑死，以免网络波动拖垮定时任务。
